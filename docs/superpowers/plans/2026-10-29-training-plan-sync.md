# Training Plan Sync Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Members create, update, view and tick the same training plans on the web and the Flutter app, through one plan generator.

**Architecture:** The web's pure generator is gathered into `plan-core.ts` and copied verbatim into hono-workers by a sync script. One new API endpoint, `POST /me/apps/nubi/plan-build`, turns plan inputs into dated weeks. Storage, ticks, the active plan and walk mode keep using the existing `/me/apps/nubi/plan` and `/me/apps/nubi/active` records. The app renders whatever the API returns and deletes its own generator.

**Tech Stack:** Astro + TypeScript + bun check scripts (web); Hono on Cloudflare Workers + bun verify scripts (API); Flutter + Riverpod 3 + Dio (app).

**Spec:** `docs/superpowers/specs/2026-10-29-training-plan-sync-design.md` (nubisport-flutter)

## Global Constraints

- The stored format must not change: `{engine, data, progress}` in `nubi/plan`; `{engine, data: {plan, jalan?}, progress: []}` in `nubi/active` under key `plan`. Plan keys, quotas (free 1 / ahli 5 / admin 10) and `ENGINE_VERSION = 2` semantics stay the same.
- Tick token = `"<week no>.<session index>"`.
- Web behaviour stays unchanged, including signed-out (localStorage) plans. Every existing `scripts/check-*.ts` in nubisport-astro still passes, and `astro build` still succeeds.
- The engine copies in hono-workers are never hand-edited. They are generated by `bun scripts/sync-plan-engine.ts` in nubisport-astro.
- hono-workers has unrelated uncommitted work (`docs/telegram.md`, `scripts/verify-telegram.ts`, `src/services/telegram.ts`). Never stage or modify those files.
- Each repo works on a branch `feat/plan-sync`. Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- App copy is in Malay and matches the existing screens. Flutter code is formatted with `dart format -l 120` on touched files only.

## Review Focus

1. **Saved plan without `mula` (old plans):** sessions have `tarikh: null`. The app shows week/session lists without dates and doesn't crash (Task 4 and Task 5 tests `undated plan`).
2. **Server timezone:** Workers runs in UTC and members are in Malaysia (UTC+8). The same inputs must produce identical `tarikh` values under `TZ=UTC` and `TZ=Asia/Kuala_Lumpur` (Task 3 verify check `same output in UTC and MY`).
3. **Plan saved with another engine version:** the app opens it read-only with "Pelan ini dari versi lama. Buka di web untuk sambung." and no tick boxes (Task 5 test `engine mismatch is read-only`).
4. **Quota full on create (409):** the app offers to replace one existing plan, then saves with `?replace=` (Task 6 test `quota full offers replace`).
5. **Tick save fails (offline / 5xx):** the tick rolls back and a SnackBar shows "Tak dapat simpan tanda. Cuba lagi." (Task 6 test `failed tick rolls back`).

**Interfaces:**
- Consumes: Task 1 exports via `./engine/plan-core`, plus `calcMaf` from `./engine/maf`.
- Produces: `buildPlanResponse(input: PlanBuildInput): { ok: true; data: PlanBuildData } | { ok: false; error: string; cadanganBulan?: number; cadanganMinggu?: number }` in `build.ts`, where
  - `PlanBuildInput = { kind: '5k'|'10k'|'21k'|'42k'; params: Record<string,string>; key?: string; previous?: { params: Record<string,string>; progress: string[] }; walkUntil?: string | null }`
  - `PlanBuildData = { engine: number; key: string; params: Record<string,string>; amaran: string[]; progress?: string[]; weeks: { no: number; fasa: string; ringan: boolean; minit: number; sesi: { id: string; tarikh: string | null; jenis: string; minit: number; tajuk: string; arahan: string; usaha: string; walk: boolean }[] }[] }`
- HTTP: 200 `{success:true, data: PlanBuildData}`; 400 `{success:false, error, cadanganBulan?, cadanganMinggu?, field?}`; 413 when body > 16 KB.
- How the build works:
  - `params = normalizePlanParams(kind, input.params)`.
  - If `params.umur && params.keadaan`, use `calcMaf(Number(umur), keadaan)`; `!ok` → error `"Ikut nadi: " + sebab`; otherwise `nadi = {maf, bawah}` goes to the builder. This mirrors `Plan5k.astro:389-399` and `DistancePlan.astro:348-359`; use `buildFromParams` with `nadi` added, or call `buildPlan` / `buildDistancePlan` directly the same way.
  - `key = planKeyFor(kind, params, input.key)`.
  - Session dates and walk flags come from `planSessions(key, params, walkUntil)` matched by `id` (null when no `mula`). Titles and effort are taken from `planSessions` when `walk` is true, otherwise from the session.
  - `progress = remapProgress(previous.progress, planFromParams(key, previous.params).minggu, built.minggu)` when `previous` is given and builds.
- Validator (zod, via `parse` from `validators/common`): `kind` enum; `params` ≤ 20 keys matching `/^[a-z0-9_]{1,24}$/` with string values ≤ 100 chars; `key` matches `ITEM_KEY`; `progress` ≤ 300 tokens matching `/^[a-z0-9._-]{1,16}$/`; `walkUntil` is ISO date or null.
- Route middleware: `jwtAuth`, `requirePermission('account.read')`, `bodyLimit({maxSize: 16*1024})`. Set `Cache-Control: no-store`.
